### Deviation from plan (documented)

**`TestPAdESModificationDetection.java` was NOT ported** to `afirma-crypto-pdf`.

- **Reason:** it depends on `es.gob.afirma.signvalidation.{ValidatePdfSignature, SignValidity}`, which live in `afirma-crypto-validation`. Since `afirma-crypto-validation` *depends on* `afirma-crypto-pdf`, adding it as a test dependency would create a **Maven reactor cycle** (`ProjectCycleException`).
- **Disposition:** modification/shadow-attack detection already exists as `afirma-crypto-validation/.../signvalidation/TestPdfMods.java`. It is NOT duplicated downward. This test remains in its natural module.
- **Consequence:** vector files `RFE023 - Formulario_prueba_PDF_mod.pdf`, `RFE023 - shadow form.pdf` remain available in the pdf module but are currently unused by any pdf-module test. `Ejemplo_PDF_Shadow_Attack_1.pdf` was not copied.

### Cyclic-dependency resolution (design decision)

`afirma-crypto-validation` depends on `cades`, `cms`, `pdf`, `xades`. To validate signatures *inside* those lower modules without a cycle, validation entry points were made **public and self-contained** in main sources:

- `afirma-crypto-cms/.../signers/cms/ValidateCMSSignedData.java` — class made `public`; static `validate(byte[], boolean)` added.
- `afirma-crypto-cades/.../signers/cades/CAdESValidator.java` — static `validate(byte[], boolean)` + inner `ValidationResult` added.
